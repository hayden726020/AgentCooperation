# 项目长期记忆与状态持久化系统 (Memory Systems)

AI 本身不具备跨会话的隐式物理记忆。为了让项目在长期迭代中保持架构一致性、避免新会话遗忘已完成功能，必须将记忆**显式文件化**并沉淀在版本控制中。

## 一、三层知识体系划分

| 知识分层 | 存储位置 | 更新频率 | 加载时机 | 典型内容 |
| :--- | :--- | :--- | :--- | :--- |
| **第一类：长期稳定知识** | `docs/architecture.md`<br/>`.planning/PROJECT.md` | 低频（仅在架构演变时） | 新会话按需加载摘要 | 架构分层、核心协议契约、单引擎互斥规则、预算硬约束 |
| **第二类：动态工作状态** | `.planning/STATE.md`<br/>`.planning/ROADMAP.md` | 高频（每任务完成后） | 会话冷启动必读 | 当前开发阶段、刚刚完成的检查点、当前阻碍点、下一步具体任务 |
| **第三类：详细历史资料** | `docs/archive/`<br/>`.runtime/logs/`<br/>SQLite `execution_logs` | 持续追加 | 仅在专项排查时检索 | 历史长篇验收报告、旧版本压测日志、详细终端调用 trace |

## 二、架构决策记录模板 (ADR: Architectural Decision Records)

当发生重大技术选型、重构或废弃旧逻辑时，在 `docs/decisions/` 或 `.planning/codebase/` 记录 ADR：

```markdown
# ADR-[编号]: [决策标题]

* **状态**: [提议 / 已采纳 / 已废弃]
* **日期**: YYYY-MM-DD
* **决策背景 (Context)**: 遇到了什么问题，原机制为何无法满足需求。
* **决策内容 (Decision)**: 选择了何种技术方案、数据结构或流程。
* **积极影响 (Consequences - Positive)**: 获得了什么收益（如性能提升、降低上下文）。
* **代价与风险 (Consequences - Negative)**: 带来了什么妥协或需要后续注意的事项。
```

## 三、记忆一致性铁律

1. **代码事实高于文档宣称**：若文档记载的功能在源码中不存在或测试报错，必须以可复现的代码事实为准，并立即纠正文档。
2. **任务结束必同步**：每次完成代码修改并验证通过后，必须在同一提交或交接中更新 `.planning/STATE.md`。
