# GSD (Git. Ship. Done.) 工程开发与质量控制全流程规范

本规范是项目统一的开发工作流与质量标准，整合 GSD 的结构化流程管理与 Superpowers 的高标准工程质量实践。统一遵循：**项目状态外部化、任务原子化、断点可恢复、TDD 测试先行、根因调试、安全交付**。

---

## 一、已有项目安全接管三步法 (Takeover Protocol)

对于存量项目，严禁盲目重构，必须严格按顺序只读接管：

1. **建立安全恢复点**：
   - 检查工作区状态（`git status`），绝对不覆盖未提交代码。
   - 对未提交文件生成 patch 备份至安全目录（如 `.runtime/backup/`）。
   - 为当前 HEAD 创建备份快照分支（如 `backup/pre-optimization-<date>`）。
   - 导出环境依赖版本基线（`pip list` / `node -v`）。
   - 运行既有测试套件，锁定最初的测试通过率基线。

2. **只读审计与模块映射**：
   - 梳理目录结构、核心入口、模块依赖与数据流。
   - 审计多 Agent 调度、超时判定、重复执行保护与错误处理机制。
   - 建立功能完成矩阵（A 到 F 级状态评级）。

3. **初始化文件化规划系统 (`.planning/`)**：
   - `.planning/PROJECT.md`：锁定核心目标与技术边界。
   - `.planning/ROADMAP.md`：阶段化开发演进路线图。
   - `.planning/STATE.md`：当前执行状态与下一步行动。
   - `.planning/codebase/`：代码库架构、接口契约与审计报告。

---

## 二、阶段任务拆解准则 (Task Atomization)

所有任务规划与进度跟踪**唯一受控于 `.planning/` 目录**，严禁创建任何其他格式的 plan/todo 文件。每个原子任务必须具备五要素：

1. **明确的目标（Goal）**：一句话定义要实现的能力或修复的问题。
2. **有限的代码修改范围（Bounded Scope）**：通常只涉及 1-3 个具体文件，严禁一次性修改跨层模块。
3. **技术约束（Constraints）**：保持已有接口签名兼容，遵循单 Flash 引擎或预算限额。
4. **可执行的验证命令（Verification Command）**：指定具体的测试命令。
5. **清晰的完成标准（Done Criteria）**：目标测试全绿，全量回归 0 失败。

---

## 三、微观执行：测试驱动开发 (TDD) 铁律

在执行具体任务编写代码时，严格遵循三步循环：

1. **红灯先行 (Red Phase)**：在修改任何功能代码之前，先编写或补充能够准确复现问题或断言新功能的测试用例。执行测试，确认其以预期的断言原因失败。
2. **绿灯最小实现 (Green Phase)**：编写满足该测试的最小充分代码，避免过度设计。再次执行测试，确认变为通过。
3. **安全重构 (Refactor Phase)**：在测试全绿的保护下重构代码，消除重复逻辑，并保证测试持续全绿。
4. **严禁弱化测试**：严禁通过删除断言、降低判定标准或直接 skip 测试来换取表面上的“全绿”。

---

## 四、疑难问题：根本原因调试法 (Root-Cause Debugging)

遇到异常或测试报错时，禁止无依据盲猜盲改，按四步排查：

1. **定位精确证据**：从完整 traceback 中提取最初发生异常的代码行号与输入参数，确认是参数契约问题、状态机不匹配还是异步时序问题。
2. **最小复现用例**：编写最小单元测试隔离该问题，排除复杂外部依赖。
3. **因果分析**：定位根本原因（如是配置解析错误，还是底层进程未及时回收），而非仅在表层加 `try...except` 吞掉异常。
4. **验证修复**：修复后不仅运行该用例，还需运行相关联的模块测试，确认未破坏兄弟功能。

## 五、安全交付十步闭环清单 (Verified Delivery Checklist)

任何功能交付或 Git 提交前，逐一核对：
1. [ ] 任务目标与完成标准明确对齐。
2. [ ] 仅修改了限定的文件范围，未触碰未授权模块。
3. [ ] 敏感凭据（API Key / Token / 密码）未硬编码或输出到日志中。
4. [ ] 目标功能测试通过，且有明确断言覆盖。
5. [ ] 运行全量离线回归测试（`python -m pytest tests/ -q -p no:cacheprovider`）0 失败。
6. [ ] 审查 `git diff`，确认无无用空格、测试残余文件或多余 print 日志。
7. [ ] 未破坏向后兼容性与公开接口签名。
8. [ ] 代码通过独立只读复核，未检出 P0/P1 风险。
9. [ ] 更新 `.planning/STATE.md` 与相关文档。
10. [ ] 生成语义化 Git commit message。

---

## 六、跨会话恢复协议 (Cross-Session Resumption)

在新会话启动时，AI 无需重新阅读全部历史聊天记录，按以下顺序零成本恢复：

1. **读取状态摘要**：首先只读 `.planning/STATE.md` 与 `.planning/ROADMAP.md`，明确当前处于哪个阶段、上一任务的完成情况与阻碍点。
2. **按需检索代码**：根据待办任务读取 `.planning/codebase/architecture.md` 定位相关模块，仅打开目标文件，不遍历整个仓库。
3. **执行闭环**：修改代码 -> 运行相关靶向测试 -> 运行全量离线回归 -> 更新 `.planning/STATE.md` -> Git 提交。
