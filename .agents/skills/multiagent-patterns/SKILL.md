# 多 Agent 协同与上下文隔离模式 (Multi-Agent Patterns)

多 Agent 协同的核心在于**职责单一、上下文物理隔离、只读结构化交接、阻断性安全门禁**。坚决防止“传话游戏”（Telephone Game）带来的上下文失真。

## 一、三角色职责边界与隔离矩阵

```
                ┌──────────────────────────────────────┐
                │          Orchestrator Agent          │
                │   需求分析、任务拆分、调度与最终验收    │
                └───────────┬──────────────▲───────────┘
                            │ 派发任务      │ 结构化裁决
                            │ (Worktree)   │ (ReviewVerdict)
                ┌───────────▼──────────┐   │
                │    Developer Agent   │   │
                │  工作树内编码与本地测试 │   │
                └───────────┬──────────┘   │
                            │ 传递只读产物   │
                            │ (Artifacts)  │
                ┌───────────▼──────────────┴───────────┐
                │           Reviewer Agent             │
                │      只读复核 diff 与真实测试证据      │
                │        (GLM / DeepSeek Flash)        │
                └──────────────────────────────────────┘
```

1. **主调度 Agent (Orchestrator)**：
   - 负责任务规划、状态机流转控制、预算守护（¥200/月）与人工审批中继。不直接书写业务实现细节。
2. **执行研发 Agent (Developer)**：
   - 运行在专属 Git 工作树内，拥有读写工具与本地测试权限。负责实现代码与测试，生成提交检查点。
3. **独立审查 Agent (Reviewer)**：
   - **绝对只读**，不具备写文件或执行命令权限。仅根据研发传出的 Commit SHA、脱敏 Git diff 和真实测试日志返回 `ReviewVerdict`。

## 二、交接契约与防污染规则

1. **结构化证据交接 (`DevelopmentArtifacts`)**：
   - 研发向审查交接时，禁止传递研发 Agent 的完整对话历史或中间思考过程。
   - 仅传递高价值结构化数据：`commit_sha`、`base_ref`、`git_diff`（脱敏后）、`test_passed`、`test_summary`。
2. **审查裁决与安全拦截 (`ReviewVerdict`)**：
   - `P0` 严重安全或破坏性风险：**立即阻断，挂起为 `WAITING_APPROVAL`，必须由人类操作员显式授权**，禁止自动化继续打补丁。
   - `P1` 核心缺陷：附带具体缺陷原因，触发有界自修（Bounded Repair，默认 <= 3 次）。
   - `P2/P3`：普通代码优化建议，允许测试通过后交付。
3. **超时与重复执行保护 (Timeout Idempotency)**：
   - 当调用超时被看门狗杀死后，系统不能盲目认为任务失败立即重试。
   - 必须通过状态探针检查远端或工作区是否已产生提交，确认状态后再做决定，防止重复提交或扣费。
