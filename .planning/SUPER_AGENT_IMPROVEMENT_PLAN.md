# AgentCooperation 持续型 Agent 改进方案

日期：2026-11-03。状态：方案，尚未实施。依据：[DeepSeek Super-agent 架构文章](https://x.com/DeepSeekHarness/status/2116857257245987236?s=19)、[卡兹克自动化系统实践](https://x.com/Khazix0918/status/2117054043868860521?s=19)、本仓库源码与 `.planning/STATE.md`。DeepSeek 的[公开原型](https://github.com/deepseek-ai/dsh-superagent-prototype)只作为设计参考；其 README 明示它是面向单个 GitHub 仓库的研究原型，部分文章设计尚未实现。

## 目标与边界

把现有“用户发起一次研发任务”的闭环，逐步扩展为“可信事件可触发、后续消息可续办、异常可恢复、仅必要时打扰用户”的系统。保留现有 Python/SQLite、CLI/Web/Hermes 入口、单任务 GLM 或 DeepSeek 二选一规则，以及手动 Hermes Profiles 的独立角色配置。先面向单机和已授权仓库，不把云端常驻、多租户、自动发布作为首期目标。

## 现状对照

| 两篇文章的能力 | 当前可复用实现 | 实际缺口 |
| --- | --- | --- |
| Agent 执行、独立复核、测试与预算 | `orchestrator/core.py`、`orchestrator/gemini_closed_loop.py`、`orchestrator/budget_guard.py` | 两条编排入口的任务与证据契约尚未统一；真实执行隔离仍待 M5 验证 |
| 任务过程、历史和人工审批 | `execution/events.py`、`storage/models.py`、`web/api.py`、`web/run_service.py` | 运行事件是任务输出，不是外部触发事件；跨入口审批仅有进程内占用 |
| 防重复 | Hermes bridge 的 `IdempotencyRecord` | 去重没有覆盖 Web 和未来的外部事件入口；需区分投递 ID 与同一对象后续消息 |
| 并发执行 | Git worktree、`web/runner.py` 后台线程 | JobManager 状态只在内存中；重启后无可靠领取、租约和恢复 |
| 事件路由与上下文连续性 | 仓库白名单、项目上下文定向加载 | 缺外部事件模型、来源鉴权、规则路由、Thread→Task 关联和后续消息续办 |
| 主动巡检与异常恢复 | 工作树超时探针、运行状态与事件流 | 缺独立的任务进度监测和卡住后的明确处置流程 |

## 建议架构

`外部来源/定时检查 → 来源鉴权与规则过滤 → 持久化 Trigger/Thread → 派发与租约 → 现有编排器/工作树 → 测试及独立复核 → 运行台审批/结果`。

“协调层”只负责识别来源、关联任务、派发和呈现结果，不直接改代码。先采用确定性规则；仅在规则无法判断且已有明确预算时，增加模型语义判断。已有任务的后续事件按 Thread 关联送到该任务；如果执行器暂不支持运行中追加输入，则保存为待办输入，在安全检查点续办，不能偷偷拼接到正在运行的模型上下文。每条事件只内联 ID、摘要与必要邻近信息，长内容保留引用并按需读取。

## 分阶段实施与验收

### P0：先完成现有闭环的可靠性门槛

范围：`storage/`、`orchestrator/gemini_closed_loop.py`、`web/run_service.py`、执行环境与 M5 验收。用数据库条件更新或跨进程锁保证同一 `WAITING_APPROVAL` 任务只能被一个入口领取；确认模型可写代码的隔离方案；在获准的真实环境验证 `agy` 钩子的放行、拒绝和审计；补齐运行台写接口访问边界。这里的真实调用、长期服务与外部部署分别按用户授权执行。

验收：两个独立进程同时批准同一任务时恰好一次进入修复且只预留一次预算；失败可回到可解释状态；隔离环境内的恶意测试无法读取宿主凭据或写出允许范围；真实钩子证据与运行台审计一致。离线模拟不能替代最后一项真实验收。

### P1：一个来源的事件试点

范围：增加 `Trigger`、`Thread`、`Dispatch` 的持久化记录及一个只读/低风险来源适配器。首选已经有清晰对象 ID 和可回链的来源，例如指定仓库的 GitHub Issue；若外部连接未获授权，先用固定样本在 Mock 环境演练。记录 `source`、`event_id`、`thread_id`、`object_id`、`type`、`summary`、`url`、`received_at`、`policy_version`、`task_id` 和处理状态。保存原始载荷时要限量、脱敏并设置保留期。

默认采取“仅记录”模式；通过白名单、签名/凭证校验和规则匹配后，才允许创建任务。对 `(source,event_id)` 建唯一约束以处理重复投递；对同一 Thread 设置单任务占用和有界并发。派发仍调用现有任务创建入口，不另造研发执行链。

验收：重复投递不会生成第二个任务或预算预留；不同事件属于同一 Thread 时可关联到原任务；未授权来源与规则外事件不能触发执行；进程重启后待派发事件可恢复，失败有可见原因。

### P2：续办、决策与安静通知

为任务增加后续输入队列及关联记录，区分“补充信息”“改变方向”“取消”和“新任务”。在运行台统一显示事件、任务、复核证据与审批建议；只对确需用户判断的事项通知。把用户明确作出的决定连同时间、范围和来源保存为决策记录，复用前检查适用范围。通知渠道先用现有 Web UI；飞书等外部消息集成作为独立后续阶段。

验收：任务进行中收到补充消息不会丢失或污染其他任务；取消请求可到达安全停止点；用户收到的审批含原因、建议和批准后的具体动作；历史页面可从事件跳到任务，再回到来源对象。

### P3：进度监测和选择性主动工作

在持久化任务状态上增加心跳、最后实质进展时间、重试次数和失败分类。先由确定性 Watchdog 标记卡住、超时、反复失败与租约过期，再由人工或有界规则决定重试；语义判断仅在误报/漏报数据足够时加入。主动工作从只读诊断和草稿开始，记录“本来会做什么”的观察结果，评估通过后再开放代码修改。

验收：模拟进程崩溃、事件重复、模型超时和任务空转时均能检测并给出唯一的下一步；没有无限重试；每次主动触发都能追溯来源规则和费用。

### P4：按实际规模扩展

只有 P1–P3 的任务量和延迟数据显示瓶颈时，才考虑多机 worker、云端协调层、批量路由、独立 CI 中台或自动发布。任何远端执行都要单独设计身份、最小权限、凭据不可进入模型上下文的机制，以及断线恢复。文章中的 Router 性能数字来自模拟工作负载，不能作为本项目容量承诺。

## 实施顺序与决策点

每阶段只做一个纵向场景，先写失败测试，再实现，运行靶向和相关离线回归并安排独立复核。P0 后决定能否允许自动触发代码修改；P1 后用重复率、漏派率、人工介入次数、费用、任务完成时间和恢复成功率决定是否进入 P2。若首个事件来源未能稳定运行，不扩大来源数量。`README`、架构图和旧运行台方案中已出现状态不一致，实施时以代码与测试为准同步现役文档。

本方案只读检查了当前代码与公开文档，未运行测试、真实模型或第三方原型。现有工作区有大量未提交改动；实施前应保留并核对，不能直接覆盖。
